2. LSVID 層數 L0–L2 vs L1–L4 雙重編號成立・已定位根因

教授的意見

正文用 L0–L2 且數值較大（L0 鑄造 143.72 μs、驗證 915.35 μs）；表 10 用 L1–L4 且數值小得多（L1 擴展 24.94 μs、L2 驗證 118.23 μs）。 教授猜測差異可能來自：增量 vs 累計、函式內部 vs 完整成本、平均 vs 中位、或不同批次／硬體。

✓ 意見成立。根因有兩個，而且都不是教授猜的「增量 vs 累計」。

根因 A：repo 裡有兩套獨立的量測工具，論文各取一套

3. CVE 拒絕率的小樣本與分母問題成立・且發現真實程式缺陷

教授的意見

75.0%／33.3%／25.0% 的分母很小（3/4、1/3、1/4）；要求在表 12 附近標出各類別的 (rejected / total) 原始計數；並質疑「分母排除 n/a」的規則是否系統性偏袒所提架構。

查證結果

✓ 意見成立。而且 aggregator 有一個教授沒看到的真實缺陷 —— 但偏袒方向與他擔心的相反。

好消息：原始計數本來就已經算出來了，論文只是沒印

scripts/security/aggregate-security.py 第 10 行：
sheet "by_category" — category × stack, cell = "rejected/total"

aggregator 產出的 xlsx 內，by_category 分頁已經是 rejected/total 格式， 且 REJECT／ACCEPT／total／reject_rate 四個欄位全都有輸出（第 89–92 行）。 教授要的東西不用重跑實驗，把既有 xlsx 的欄位補進表 12 即可。

壞消息：skipped 被算進分母 —— 這是 bug

aggregate-security.py 第 57–63 行 normalise_verdict()： 不在 ACCEPTED／REJECTED 集合內的 verdict 一律 return v.upper()
第 89–90 行：g["total"] = g.sum(axis=1) → 把 SKIPPED 欄一起加進 total
reject_rate = REJECT / (REJECT + ACCEPT + SKIPPED)

依 probe-paper5-attacks.sh 第 14–19 行的定義，skipped 意思是 「preflight 工具缺失，不構成對防禦的判定」（例如該 host 沒裝 tcpreplay／gcc）。 但它現在被當成「沒擋下」灌進分母，系統性地壓低拒絕率。

方向值得注意：這個缺陷對所提架構不利，而非偏袒。但它同時讓兩個 stack 的百分比失去可比性 —— 如果 A stack 的 host 裝了 tcpreplay 而 B stack 的沒裝，兩者的分母根本不是同一回事。 這一點必須修，且修完數字會變動，要重新產表。

另一個既有的良好設計（可主動寫進論文，展現嚴謹）

is_attack=0 的控制案（happy path、health 端點、replay 首發） 已被 aggregator 自動排除在 reject_rate 之外（第 80–82 行 _attacks_only()）， 且 scripts/security/README.md 明載其用途是驗證環境健康（A9 必須 accept，否則整個 stack 不健康、結果不可採信）。 這是紮實的實驗衛生，論文應該寫出來。

建議動作

  1. 修 normalise_verdict／category_summary，把 SKIPPED 排除在 total 之外，並在表中另立一欄標示 skipped 數。
  2. 修完後重跑 aggregator、重產表 12。數字會變 —— 相關結論須同步更新。
  3. 表 12 每格改印 rejected/total (rate%)，資料直接取自既有 by_category 分頁。
  4. 接受教授的用語修正：「測試案例拒絕比例」，不要叫「攻擊覆蓋率」。n=3、n=4 撐不起統計語言。
  5. 明確寫出控制案排除規則與 skipped 處理規則，堵住「分母如何決定」的質疑。

4. 對照組公平性 / 容器設定混淆成立・有程式碼證據

教授的意見

SPIFFE Watcher 用了 read_only、tmpfs noexec、cap_drop ALL， Vault Server／Agent 保留預設 —— 差異可能來自容器硬化，而非架構能力。 且 Vault PKI 是傳輸層 PKI，本架構是傳輸＋應用＋業務三層，防禦面本就不同層級。

查證結果

✓ 意見成立，而且我在程式碼裡找到了讓這個混淆直接量化成分數的機制。

證據一：容器／網路設定被計為與身份層拒絕同分

aggregate-security.py 第 36–38 行：
REJECTED = {"rejected", "broker-rejected", "not-reachable", "blocked"}

not-reachable（port 根本沒開）與 blocked（網路擋掉） 和 rejected（身份層主動拒絕）被歸為同一類 REJECT。 這代表：一個 stack 只因為 compose 沒暴露某個 port，就能在拒絕率上得分， 分數與「LSVID 驗章擋下偽造身份」完全等價。這正是教授擔心的混淆，而且它是被寫死在計分邏輯裡的。

證據二：D 類（Port 暴露）每個 stack 的案例集根本不同

scripts/security/README.md §3.D：「每個 driver 自帶不同的 D 子集」
probe-linkerd.sh：D1 admin :9990、D2 :4140、D3 :4141、D4/D5 跨 host
probe-baseline.sh：D1–D4 服務裸 port、D5–D7 確認無 Linkerd 殘留、D8/D9 跨 host 直連

D 類在不同 stack 上跑的是不同的案例、不同的數量。 把各 stack 的 D 類拒絕率並排比較，等於在比較兩組不同的題目 —— 這個比較在方法學上無效， 也直接解釋了教授看到的「通訊埠暴露 50%」為何難以詮釋。

證據三：A 類與 E 類的結果與身份層無關（可用來自我辯護）

README 明載 A 類（HTTP ingress，12 案）是 stack-agnostic —— 所有 stack 打同一組案例， 所以教授看到的「HTTP ingress 0%」本來就不該有差異，這不是缺陷。

E 類（Replay，3 案）README 更是直接預告： 「沒有 idempotency key 機制下，E2/E3 都會 202 accepted。任何 stack 都擋不住是預期結果 —— 這是給 Saga 應用層該補的洞，不是身份／網路層的責任。」 這是設計時就明知並記錄的已知限制，不是實驗失誤。論文若照這個口徑寫，反而是加分項。

建議動作

  1. 照教授說的，在實驗三開頭明說這是刻意的非對稱對照，先把公平性質疑堵住。這句話成本最低、效果最好。
  2. 把三種能力分開列表：LSVID 特有（C4–C6 偽造 envelope）／SPIFFE 特有／容器與網路設定（D 類、not-reachable）。 這是回應教授的核心動作。
  3. D 類不要跨 stack 比較，或改成兩個 stack 都跑的同一組案例。維持現況等於留一個明顯破口給口試委員。
  4. 兩個 stack 套用相同容器硬化設定後重測 —— 這是最徹底的解法，但成本最高。若時間不允許，至少要在「實驗限制」誠實揭露。
  5. 正面討論共同擋不住的類別（HTTP ingress、觀測落差、replay），並引用 README 已記錄的理由。誠實揭露比粉飾更有說服力。

6. +34.9% 延遲歸因混淆成立・且中介組數據已存在

教授的意見

20,000 筆下 SPIFFE+Keycloak+LSVID（713.15s）vs Vault PKI（528.70s）的差距，被歸因於「使用者身份驗證＋授權檢查＋LSVID 鏈驗證」， 但這兩個 stack 同時差在使用者層（Keycloak）與 LSVID 兩個維度。教授指出實驗一其實有第三組「SPIFFE+Keycloak（無 LSVID）」， 應在 4.4 用它做中介比較。且同段又說主瓶頸是佇列等待、密碼學僅 3.1ms，兩個說法需調和。

查證結果

✓ 意見成立，而且好消息是：中介組的數據與分析工具都已經在 repo 裡，可以立刻做拆解。

artifacts/measure/RESULTS.md 標題：「Group B: SPIFFE+Keycloak, no LSVID」 （count=2000, concurrency=100, warm；4 次執行，completion 100.0%，saga p50 533.4→602.67 ms）
scripts/experiments/compare-three-stacks.py 已內建三方比較：
A = SPIFFE+Keycloak+LSVID（LSVID-on）／B = SPIFFE+Keycloak（LSVID-off）／LK = Linkerd 1.x

有了 B 組就能把差距拆成兩段：(Vault → B) ＝ Keycloak 使用者層的增量、 (B → A) ＝ LSVID 鏈的增量。這正是教授要的，且不需要新實驗。

另外，教授指出的內部矛盾是對的：若密碼學成本僅 3.1 ms、主瓶頸是佇列等待， 那麼 +34.9%（約 184 秒）在數量級上就不可能主要來自 LSVID 鏈驗證。 20,000 筆 × 3.1 ms ≈ 62 秒，且那還是可被平行消化的 CPU 時間。 「+34.9% 主要來自身份鏈驗證」這個宣稱撐不住，必須改寫。

⚠ 一個需要你自己判斷的疑慮（教授沒提，但口試可能被問）

compare-three-stacks.py 的 docstring 寫著： 「Target narrative (goal2.md §1): for 訂單完成時間, A < LK < B at every scale — the full-LSVID mode is the fastest」， 並產出一個 ordering_ok 欄位與 ordering_verdict 分頁「feeds the goal2.md §5 fine-tuning decision」。

這支分析腳本是朝著一個預設結論寫的，還帶有「排序是否符合預期」的驗證欄位與後續調參迴路。 這在方法學上是確認偏誤（confirmation bias）的典型形狀，若被口試委員讀到 repo 會很難解釋。 此外它預期 A（有 LSVID）比 B（無 LSVID）快，這與論文正文「LSVID 造成 +34.9% 延遲」方向相反 —— 這兩個說法不可能同時成立，建議你優先釐清。（goal2.md 已不在 repo 中，我無法讀取其內容。）

建議動作

  1. 用 compare-three-stacks.py 跑 A / B 兩組，在 4.4 明確拆出 Keycloak 增量與 LSVID 增量。
  2. 改寫 +34.9% 的歸因：依現有證據，主因應為佇列等待／系統飽和，而非密碼學成本。
  3. 釐清「A 比 B 快」與「LSVID 造成 +34.9%」的方向矛盾，確定論文要主張哪一個。
  4. 把 ordering_ok／Target narrative 這類措辭從分析腳本移除，改為中性描述。
