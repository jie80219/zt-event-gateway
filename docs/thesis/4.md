# 第四章 身份交付與簽章鏈實作

本章承第二章所述之零信任理論基礎，聚焦於本系統（zt-event-gateway）將 SPIFFE/SPIRE 身份從「取得」、「跨程序共享」到「跨服務傳遞」之實作細節。依資料流方向自下而上，本章分為三節：4.1 說明本系統如何以 PHP 原生實作 SPIFFE Workload API gRPC 客戶端，作為所有身份材料之唯一入口；4.2 描述單一 watcher 行程如何透過共享記憶體（SHM）與 seqlock 協議將 SVID 一致地交付予多個 Worker；4.3 則說明本系統設計之巢狀輕量化身份令牌（Nested LSVID），使身份憑證能跨越 AMQP 訊息佇列與 HTTP 呼叫，建構端到端之簽章鏈。

---

## 4.1 SPIFFE Workload API

### 4.1.1 實作動機

SPIFFE 標準之 Workload Endpoint 規範 [1] 要求工作負載透過 Unix Domain Socket 向本機 SPIRE Agent 建立 gRPC 雙向串流，訂閱 `FetchX509SVID` 與 `FetchJWTBundles` 兩個伺服器串流（server-streaming）RPC，以持續接收憑證輪換推送。相較於官方提供之 Go、Java、C++ SDK，PHP 生態圈並無官方支援。本研究於 `packages/php-spiffe` 套件中以 PHP 8.3 + Swow coroutine runtime 原生實作 HTTP/2 傳輸層、gRPC 框架編解碼器，以及 Workload API 客戶端，主要動機有三：

1. **對協程執行模型之完整控制**：OpenSwoole / Swow 之協程語意與一般多執行緒不同，若強行封裝 C 擴充，跨協程取消、串流錯誤傳播等路徑不易正確對齊。自行實作可確保整條串流生命週期皆於單一協程中完成。
2. **憑證輪換時之原子交換**：PHP 之 `zval` 指標賦值在單協程內為原子操作，使得「舊 SVID 服務中、新材料到達即整組替換」之熱輪換策略可以免鎖完成。
3. **與應用層狀態機整合**：本系統需將 Workload API 串流狀態（Ready/Rotating/Error）傳遞給 SHM 寫入層作為健康探針依據，自行實作能避免黑箱式 SDK 將此資訊掩蓋於內部。

### 4.1.2 串流訂閱與狀態機

本系統以 `X509Source`（`src/Spiffe/Source/X509Source.php`）作為 X.509-SVID 之訂閱者。其核心為一個單協程之 `watchLoop()`：呼叫 Workload API 客戶端的 `watchX509Svid()` 以開啟伺服器串流，並在每次應答（`X509SVIDResponse`）到達時透過 callback 原子套用新材料；串流意外結束或應答解析失敗時，以指數退避（exponential backoff）重新連線。圖 4.1-1 為此主迴圈之程式碼截圖。

**圖 4.1-1：FetchX509SVID gRPC 串流主迴圈**
`src/Spiffe/Source/X509Source.php` （L279–L335）

憑證輪換之臨界區集中於 `applyResponse()`（圖 4.1-2）。解析順序為「proto 解析 → X.509 chain 與 bundle 建構 → 選擇性驗證 → 指標交換 → 通知觀察者」。任一步拋例外時，舊有 SVID 集合仍在記憶體中有效，請求服務不中斷；唯有新材料完整通過驗證，才將 `$this->svids / $this->bundles` 整組替換並觸發 `onRotated` 回呼。此「先建後換」之語意對後續 4.2 節之 SHM 寫入器同樣重要。

**圖 4.1-2：SVID 應答解析與原子交換**
`src/Spiffe/Source/X509Source.php` （L337–L415）

X509Source 之生命週期以有限狀態機建模（圖 4.1-3）。`SourceState` 列舉 Idle、Initializing、Ready、Rotating、Error、Closed 六種狀態，並於 `allowedTransitions()` 中明確定義合法轉移矩陣：例如 Ready 僅能進入 Rotating、Error、Closed，不允許直接回到 Initializing。`hasMaterial()` 作為「本狀態下憑證是否可用」之單一判斷點，避免散落於各處之 null-check 形成競態漏洞。

**表 4.1-1 X509Source 關鍵設計決策**

| 設計面向 | 採用方案 | 理由 |
|---|---|---|
| 串流處理 | 單一 coroutine watchLoop + callback | 避免每 Worker 各開一條 gRPC 串流，抑制 SPIRE Agent 負載放大 |

| 狀態通報 | `onRotated` / `onError` 觀察者 | 供 SHM 寫入器、健康檢查、LSVID signer 共用同一事件源 |

## 4.2 跨程序 SVID 共享機制

### 4.2.1 問題背景

OpenSwoole Gateway 採 prefork 多 Worker 架構，RabbitMQ Consumer 於 Docker 2/3/4 亦為多行程部署。若每個 Worker 各自建立 Workload API 串流，將導致：(1) SPIRE Agent 之 socket 描述符與 gRPC 串流數倍增；(2) 每個串流獨立接收憑證輪換推送，其抵達時序無法對齊，可能使同一請求鏈跨越新舊憑證；(3) Agent socket 之 Unix 權限校驗（peer UID / PID）邏輯複雜化。因此本研究將「身份取得」與「身份消費」解耦：由單一長駐之 `spiffe-watcher.php` 作為 Workload API 唯一消費者，將材料寫入 tmpfs 共享目錄，Gateway 與 Worker 以唯讀方式取用。

### 4.2.2 目錄結構與原子寫入

共享目錄以 `SpiffeTableSchema` 定義，預設位於 `/tmp/spiffe-shared`（圖 4.2-1）。其結構包含：`meta.json` 承載全域狀態（version、x509_state、jwt_state、slot 計數、更新時間、最近錯誤訊息）、`x509/{0,1,...}.json` 為多 SVID 情境下之 slot 檔案（slot 0 為主憑證）、`jwt/{safeName}.json` 則以經正規化之信任域名稱為檔名鍵儲存 JWT Bundle。

**圖 4.2-1：SHM 目錄結構與 schema**
`src/Spiffe/SharedMemory/SpiffeTableSchema.php` （L7–L62）

所有 JSON 檔案皆以 POSIX 原子 rename 語意寫入（圖 4.2-2）。`atomicWrite()` 於同目錄下建立 `.spiffe_XXXXXX` 暫存檔，完成 `fwrite → fflush → fsync` 後以 `rename()` 覆蓋目標；POSIX 規範保證同檔系統之 `rename()` 對讀者呈原子可見性 [4]，讀者不會取得「寫入中途」之部分內容。最後額外對父目錄進行 `fsync()`，以確保 rename 本身對行程崩潰亦具持久性（best-effort；在不支援目錄同步之平台上靜默略過）。

**圖 4.2-2：原子寫入 — write → fsync → rename → dir fsync**
`src/Spiffe/SharedMemory/SpiffeTableSchema.php` （L86–L134）

### 4.2.3 Seqlock 協議：奇偶版本號之一致性閘

單一檔案之原子寫入不足以保證跨多個檔案之一致性：例如 `x509/0.json`、`x509/1.json`、`meta.json` 三者合起來才構成一組完整的 SVID 快照。本研究採用 Lamport 提出之 seqlock 協議 [3][7] 以 `meta.json` 之 `version` 欄位作為跨檔案一致性閘。

**寫入端**（圖 4.2-3）於 `SpiffeTableStore::publishX509()` 中實作三階段節奏：(Step 1) 將 version 遞增為奇數，透過原子寫入發布，表示「臨界區開始」；(Step 2) 逐一覆寫所有 slot 檔案並清除已淘汰之 slot；(Step 3) 再將 version 遞增為偶數，同步更新 `x509_count`、`updated_at`。

**圖 4.2-3：Seqlock 寫入端三階段**
`src/Spiffe/SharedMemory/SpiffeTableStore.php` （L36–L72）

**讀取端**（圖 4.2-4）於 `SpiffeTableReader::consistentRead()` 中實作對稱的兩次取樣：讀取 v1；若 v1 為奇數表示寫者處於臨界區，自旋 `SPIN_SLEEP_US` 後重試；執行實際讀取動作；再讀 v2；若 v1 == v2 表示讀取期間無寫者介入，回傳結果；否則重試。相較於讀寫互斥鎖，seqlock 具備「讀者不阻塞寫者、寫者不等待讀者」之特性，特別適用於憑證輪換此種寫少（每小時數次）讀多（每請求一次）之場景。

**圖 4.2-4：Seqlock 讀取端一致性迴圈**
`src/Spiffe/SharedMemory/SpiffeTableReader.php` （L262–L290）

### 4.2.4 小結

**表 4.2-1 Seqlock 協議 vs. 其他跨程序同步方案**

| 方案 | 寫者阻塞讀者 | 讀者阻塞寫者 | 多檔案快照一致性 | 本研究採用 |
|---|---|---|---|---|
| POSIX `flock` 讀寫鎖 | 否 | **是** | 需應用層協調 | 否 |
| SysV shm + semaphore | 否 | 是 | 需自行設計 header | 否 |
| Seqlock（奇偶版本） | 否 | 否 | **以版本號統一閘** | **✓** |

## 4.3 巢狀輕量化身份令牌（Nested LSVID）

### 4.3.1 為何需要 LSVID

4.1、4.2 兩節解決的是「同一 Docker 內，如何把 SPIFFE X.509-SVID 公平地交付給每個工作負載行程」之問題。然而 X.509-SVID 僅於 TLS handshake 期間證明連線雙方之身份——一旦請求經 AMQP 佇列中轉、或經 Gateway 轉發至下游 HTTP 服務，TLS 之身份資訊即告中斷。為了在非同步訊息與多層 HTTP 代理場景下延續身份保證，SPIFFE 社群提出 Lightweight SVID（LSVID） [2]：一種語意最小化之 JWS token，可直接鑲入訊息 envelope 或 HTTP header。

### 4.3.2 巢狀簽章鏈設計

本系統將每一跳所產生之新 LSVID 以 `nested` 宣告包覆前一級 raw token，形成單向向外巢套之簽章鏈：

```
L0 (Gateway 鑄造, iss=gateway, aud=worker)
  └─ L1 (Worker 擴展, nested=L0, iss=worker, aud=worker)
       └─ L2 (SpiffeLsvidFilter 擴展, nested=L1, iss=worker, aud=downstream-service)
```

每一級之 `iss` 為簽章者自身 SPIFFE ID，`aud` 為下一跳 SPIFFE ID。驗證者由根往外走訪，每一級都必須滿足三項條件：(a) 以自身 x5c header 之葉憑證完成 JWS 簽章驗證；(b) 葉憑證 Subject Alternative Name URI 等於 token 之 `iss`；(c) 前一級之 `aud` 等於本級之 `iss`（鏈延續性）。

**圖 4.3-1：LSVIDSigner 核心簽章邏輯**
`packages/php-lsvid/src/LSVID/LSVIDSigner.php` （L128–L220）

圖 4.3-1 所示之 `signInternal()` 為簽章主路徑：從 SHM 讀入當前 SVID；以 `pickAlg()` 依 EC 曲線選定 ES256/ES384/ES512；剝除呼叫端傳入之保留宣告（`iss`/`sub`/`aud`/`iat`/`exp`/`jti`/`nested`），避免偽造；自動以 SVID 之 SPIFFE ID 填入 `iss`；若 `priorRawToken` 非空則以字串形式嵌入 `nested` 宣告；最後以 `openssl_sign()` 簽章並將 DER 格式之 ECDSA 簽章轉為 JOSE 格式（R||S 連接）。

**圖 4.3-2：巢狀令牌遞迴解析**
`packages/php-lsvid/src/LSVID/LSVID.php` （L60–L136）

解析端之 `LSVID::parse()` 為遞迴結構（圖 4.3-2）。為防止惡意構造極深巢套導致 stack overflow，設定 `MAX_NESTED_DEPTH = 16`。當 payload 含 `nested` 欄位且為非空字串時，以自遞迴方式解析；最終 `chain()` 方法以 root-first 順序回傳整條祖先序列 `[L0, L1, ..., 本級]`，供驗證器走訪。

### 4.3.3 驗證器：防禦縱深

`LSVIDValidator::validate()`（圖 4.3-3）實作完整之防禦縱深流程。主控 loop 以 root-first 走訪 `chain()`：

- 對每一級呼叫 `verifyLevel()`，完成「必要宣告存在 → 葉憑證由信任 CA bundle 驗出 → JWS 簽章以葉公鑰驗通 → 葉憑證 SAN URI 等於 `iss` → nbf/iat/exp 時效 → 信任域同源」六項檢查；
- 對 `i > 0` 之每一級（擴展級）額外檢查「鏈延續性」：前一級 `nested.aud` 必須等於本級 `iss`，否則即便簽章通過也拒絕；
- 對最外層額外比對呼叫端宣告之 `expectedAudience`（本跳之 SPIFFE ID）與 `expectedSubject`（L0 之 sub，用於對齊 envelope 之 source 欄位）；
- 對最外層 JTI 查詢 `JtiReplayCache` 重放快取——注意內層級會在每個下游 envelope 中重複出現，若對內層也做重放檢查將產生偽陽性，故僅對最外層一次性驗證。

**圖 4.3-3：驗證器鏈走訪與延續性檢查**
`packages/php-lsvid/src/LSVID/LSVIDValidator.php` （L78–L177）

### 4.3.4 L2 擴展與防禦式重驗

下游 HTTP 呼叫之 L2 擴展由 `SpiffeLsvidFilter`（圖 4.3-4）於 Anser 框架之 `beforeCallService()` 切入點完成。其設計之關鍵在於「**先驗再簽**」：於呼叫 `signer->extend()` 之前，先以 validator 重新驗證 `LSVIDContext` 中之 L1 token，且 audience 必須等於「本 Worker 自身」。此步驟看似冗餘（L1 在 EventConsumer 剛入站時已驗證過一次），但在協程 context 可能被污染之情境下，此處之 re-validation 構成最後一道防線：**我們拒絕簽出一個嵌入了「可疑 L1」之 L2**。若 `LSVID_REQUIRED=1` 而重驗失敗，直接拋例外中止 HTTP 呼叫；否則降級為移除 header 繼續執行（不傳遞身份，讓下游依自身策略決定是否放行）。

**圖 4.3-4：下游 HTTP 呼叫之 L2 擴展**
`anser-gateway/Filters/SpiffeLsvidFilter.php` （L32–L116）

### 4.3.5 Context 綁定：跨協程之身份傳遞

Worker 於消費 AMQP 事件時，需將 envelope 內之 LSVID 綁定至當前協程，使得後續同一請求鏈中由應用程式碼呼叫之 MessageBus、Anser HTTP 客戶端皆能自動取用正確之 prior token（圖 4.3-5）。`EventConsumer::process()` 先以 `expectedAudience = 本 Worker SPIFFE ID` 驗證入站 token，通過後透過 `LSVIDContext::set()` 綁入 Swoole coroutine-local storage；任一工作流程中之 extend() 呼叫皆透過 `LSVIDContext::current()` 取得正確之 prior token，無需在應用層手動穿參。

**圖 4.3-5：事件消費端之 L1 驗證與 context 綁定**
`src/Worker/EventConsumer.php` （L106–L189）

### 4.3.6 Fail-Closed 策略

環境變數 `LSVID_REQUIRED=1` 啟動後，下列情況皆以拋例外中止而非降級放行：(a) MessageBus 發布時找不到 prior token；(b) EventConsumer/RequestConsumer 收到缺少 lsvid 欄位之 envelope；(c) SpiffeLsvidFilter 前置重驗失敗；(d) Gateway/Worker 啟動時 SHM 為空或過期。此策略與 4.3.4 節「先驗再簽」共同構成**「絕不製造嵌入壞 L1 之 L2」之強不變量**。

### 4.3.7 小結

**表 4.3-1 LSVID 鏈各級職責**

| 層級 | 製造者 | 傳遞介質 | aud 指向 | 主要宣告 | 驗證時機 |
|---|---|---|---|---|---|
| L0 | Gateway `createBase()` | AMQP envelope | worker SPIFFE ID | `iss=gateway`、`sub=gateway` | RequestConsumer |
| L1 | Worker `extend(L0)` | AMQP envelope | worker SPIFFE ID | `nested=L0`、eventType、traceId | EventConsumer |
| L2 | SpiffeLsvidFilter `extend(L1)` | HTTP `X-LSVID` header | 下游服務 SPIFFE ID | `nested=L1`、`level=http-call` | 下游服務入口 |

## 本章小結

本章從三個層次建構了本系統之身份交付骨幹：4.1 以 PHP 原生之 gRPC 客戶端實作 SPIFFE Workload API，取得對協程、HTTP/2 框架與錯誤恢復之完整掌控；4.2 以單一 watcher + seqlock 解決多程序架構下之共享一致性問題，使 Gateway 與 Worker 得以各自擁有同一身份快照而毋需各自訂閱串流；4.3 以巢狀 LSVID 將身份從 TLS 層延伸至 AMQP 佇列與 HTTP 呼叫，並以「先驗再簽」與 `LSVID_REQUIRED` fail-closed 策略，確保整條請求鏈之身份完整性不可偽造、不可替換。第五章將於此基礎上以實驗量化本設計對延遲、吞吐量以及安全屬性之實際影響。
