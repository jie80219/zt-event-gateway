# 實驗案例：Keycloak vs SPIFFE 三維比較

> 風格：工程實驗報告。本文件僅描述方法論、變因控制、量測流程、欄位定義與重現步驟。實驗腳本（`scripts/exp/*`、`tests/benchmark-keycloak.php`、`docker-compose.kc.yml`、`AUTH_MODE` wiring）為後續任務，不在本文件範圍。

---

## 1. 背景與目的

`zt-event-gateway` 目前採用三層零信任身份機制：

- **SPIFFE/SPIRE**：發行 X.509-SVID（mTLS 憑證）。
- **LSVID**：跨 hop 巢狀簽章鏈（L0 → L1 → L2），由 Gateway 鑄造、Worker 擴展、Filter 再擴展。
- **mTLS**：下游 HTTP 呼叫使用 SVID 雙向認證。

業務面以 Saga 模式協調分散式交易（建立訂單 → 扣庫存 → 扣款 → 完成）。為驗證此設計相對於業界主流 OIDC 中心化方案（**Keycloak**）的取捨，本案在**完整保留業務邏輯**（Saga 編排、Order/Production/User 服務、RabbitMQ 事件流、EventStoreDB 持久化）的前提下，將身份層替換為 Keycloak JWT 並進行三項量化實驗：

| 實驗 | 比較對象            | 主軸                                         |
| ---- | ------------------- | -------------------------------------------- |
| 1    | Keycloak vs SPIFFE  | 端到端延遲 / 吞吐                            |
| 2    | Keycloak vs SPIFFE  | 安全性（攻擊向量矩陣）                       |
| 3    | LSVID vs X.509-SVID | 儲存空間（at-rest / wire / per-hop / cache） |

## 2. 共通實驗設定

### 2.1 Treatment Groups（四組）

三個實驗統一跑下列四組以維持一致性：

| 代號       | 名稱                   | `SPIFFE_ENABLED` | `LSVID_ENABLED` | `SPIFFE_MTLS_ENABLED` | `AUTH_MODE`（新增） | 身份載荷              |
| ---------- | ---------------------- | ---------------- | --------------- | --------------------- | ------------------- | --------------------- |
| **A**      | Baseline 無身份層      | 0                | 0               | 0                     | none                | 無                    |
| **B-mtls** | SPIFFE X.509-SVID only | 1                | 0               | 1                     | spiffe              | mTLS（cert + key）    |
| **B-full** | SPIFFE + LSVID（現行） | 1                | 1               | 1                     | spiffe              | mTLS + LSVID L0→L1→L2 |
| **K**      | Keycloak JWT           | 0                | 0               | 0                     | keycloak            | RS256 JWT (Bearer)    |

> 「保留業務邏輯」= `Sagas/OrderSaga.php`、`src/EventBus.php`、`Services/*` 完全不動，僅切換身份層 wiring。已知 swap 點集中於 5 個檔案：`bin/gateway.php`、`bin/worker.php`、`anser-gateway/Filters/SpiffeLsvidFilter.php`、`src/Worker/RequestConsumer.php`、`src/Worker/EventConsumer.php`，皆已透過 registry 抽象。

### 2.2 控制變數

- **硬體**：單一台主機跑 4 個 Docker（CLAUDE.md 部署拓撲），固定 CPU / RAM / 網路。
- **訊息中介**：RabbitMQ 配置不變，同一 vhost、同一 prefetch。
- **下游服務**：Order / Production / User 服務碼不變，僅切換 filter 中的識別協定。
- **載荷**：`STRESS_PRODUCT_COUNT=1`（單品項訂單）作為基準，保留 `=10` 作為大載荷對照組。
- **Warmup**：每組執行 200 筆預熱、丟棄前 50 筆，再進入正式量測。
- **重置**：每組之間 `docker compose down -v` 清空 RabbitMQ queue 與 EventStoreDB stream，避免背景負載污染。

### 2.3 Keycloak 環境（K 組專用）

- **Image**：`quay.io/keycloak/keycloak:26.0`，併入 `docker-compose.kc.yml`，profile = `kc`。
- **Realm**：`zt-realm`。
- **Clients**：`gateway`、`worker`、`order-service`、`production-service`、`user-service`，皆為 service-account 模式（`client_credentials` grant）。
- **Token**：RS256，TTL = 1800s（與 LSVID 預設一致）。
- **驗證模式**：**純 JWKS 本地驗證**（不使用 introspection），反映微服務間最常見配置。各服務啟動時拉一次 JWKS 並本地快取 24h。
- **TLS**：HTTPS 由 nginx sidecar 終止；K 組為 server-auth + JWT bearer（與 B-mtls 用 client cert pinning 對等）。

### 2.4 量測平面（不跨組變動）

| 平面              | 工具 / 路徑                                                            |
| ----------------- | ---------------------------------------------------------------------- |
| HTTP ingress 延遲 | `scripts/stress_test.sh`（既有，curl + xargs 並發）                    |
| Saga e2e 延遲     | `scripts/e2e-full-architecture.sh` Phase 7 Test 26                     |
| 百分位計算        | `scripts/e2e-full-architecture.sh:1138-1183`（既有 Python percentile） |
| 微基準            | `tests/benchmark-lsvid.php`、新增 `tests/benchmark-keycloak.php`       |
| 儲存空間          | `scripts/perf-suite/storage.sh`（既有）                                |

## 3. 實驗 1：延遲（Latency）

### 3.1 命題

在相同流量下，量化身份層對 e2e 交易延遲的成本。SPIFFE+LSVID 因每跳本地簽章/驗章引入固定 µs 級開銷；Keycloak 純 JWKS 驗證的單顆 token 成本較低，但無鏈路追蹤副作用。本實驗給出可比較的數據。

### 3.2 量測指標

| 指標                                            | 工具                               | 出處                                                                  |
| ----------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| HTTP 入口 → 200 OK 延遲（ms）                   | `curl -w %{time_total}`            | `scripts/stress_test.sh:229-259`                                      |
| Saga e2e（request → `OrderSagaCompletedEvent`） | worker log timestamp 差            | `e2e-full-architecture.sh:1185-1254`（Phase 7 Test 26）               |
| 單請求 P50 / P90 / P95 / P99                    | Python percentile（既有）          | `e2e-full-architecture.sh:1138-1183`                                  |
| 吞吐 req/s                                      | `stress_test.sh` xargs concurrency | 既有                                                                  |
| 身份操作 µs/op                                  | benchmark 微基準                   | `tests/benchmark-lsvid.php`、`tests/benchmark-keycloak.php`（待新增） |

### 3.3 量測點（四個）

1. **微基準（離線）**：對單一身份操作（mint / extend / validate）跑 5,000 次平均，輸出 µs/op 與 ops/sec。複用 `benchmark-lsvid.php` 格式。
2. **單請求延遲**：30 筆順序請求、無並發，量測 ingress 延遲（沿用 Phase 7 Test 24）。
3. **壓力延遲**：1,000 筆請求 / concurrency=10 / 5 次重跑，取中位數。`stress_test.sh` 接受 `STRESS_TREATMENT=A|B-mtls|B-full|K` 標籤寫入 JSON。
4. **Saga 完整生命週期**：100 筆 Saga，量測 `OrderCreateRequestedEvent` → `OrderSagaCompletedEvent` 整段（沿用 Phase 7 Test 26）。

### 3.4 變因控制

- 同一台主機、依序執行 A → B-mtls → B-full → K，每組之間完全 teardown。
- `RABBITMQ_PREFETCH`、`SAGA_TIMEOUT_MS`、`HTTP_TIMEOUT` 全部固定。
- 不在實驗窗口跑其他壓力測試或 CI。

### 3.5 預期輸出

```
docs/data/exp1-microbench-{treatment}-{ts}.json   # 微基準
docs/data/exp1-latency-{treatment}-{ts}.json      # 壓力測試 raw + 百分位
docs/data/exp1-saga-e2e-{treatment}-{ts}.json     # Saga e2e
docs/data/exp1-summary.csv                         # 聚合比較
```

JSON schema（壓力測試輸出沿用 `stress_test.sh:229-259`）：

```json
{
  "treatment": "B-full",
  "total": 1000,
  "concurrency": 10,
  "success_rate": 0.998,
  "p50_ms": 12.3,
  "p90_ms": 24.5,
  "p95_ms": 31.2,
  "p99_ms": 48.9,
  "throughput_rps": 412.5,
  "http_codes": { "200": 998, "500": 2 }
}
```

### 3.6 重現步驟

```bash
# 後續任務需先建立 scripts/exp/run-latency.sh 與 docker-compose.kc.yml
for T in A B-mtls B-full K; do
  AUTH_TREATMENT=$T scripts/exp/run-latency.sh    # 包裝 stress_test.sh + 微基準 + Saga e2e
done
scripts/exp/aggregate-latency.py                  # 產生 summary.csv 與 matplotlib 圖
```

## 4. 實驗 2：安全性（Security）

### 4.1 命題

以攻擊向量矩陣量化兩種身份方案在「身份偽造、鏈路追蹤、重放、金鑰外洩、信任域隔離」上的防禦覆蓋。LSVID 的巢狀鏈與 jti replay cache 提供 Keycloak 預設無法提供的能力；Keycloak 的中央化在 blast radius 與輪換上有結構性差異。

### 4.2 攻擊向量矩陣

對 A / B-mtls / B-full / K **每一組**注入下列攻擊（以 `scripts/e2e-full-architecture.sh` Phase 5 的測試手法擴充）：

| ID      | 攻擊向量                                                     | SPIFFE+LSVID 預期                                            | Keycloak 預期                                   | 備註                |
| ------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ----------------------------------------------- | ------------------- |
| **S1**  | 偽造 issuer（跨信任域 SPIFFE ID / 跨 realm JWT）             | 拒絕（trust domain 比對）                                    | 拒絕（iss 比對）                                | Phase 5 Test 17, 20 |
| **S2**  | 篡改 audience（誤投遞至非預期下游）                          | 拒絕（aud claim）                                            | 拒絕（aud claim）                               | 新增                |
| **S3**  | 過期 token                                                   | 拒絕（exp + 30s skew）                                       | 拒絕（exp）                                     |                     |
| **S4**  | Replay 同一 jti / token                                      | 拒絕（`JtiReplayCache`）                                     | **通過**（純 JWKS 驗證無 replay 防禦）          | **關鍵差異**        |
| **S5**  | 中間節點竄改 payload（鏈中間段）                             | 拒絕（每層獨立簽章 + nested 雜湊比對）                       | N/A（扁平 JWT 無鏈）                            | LSVID 獨有          |
| **S6**  | 跳過中間節點直接呼叫下游（Worker → Service skipping Filter） | 拒絕（L2 audience 必須是下游 SPIFFE ID）                     | 部分通過（JWT 任何持有者可重用）                | **關鍵差異**        |
| **S7**  | 私鑰外洩，攻擊者偽造身份                                     | Blast radius = 該 SPIFFE ID 一個工作負載；SPIRE TTL 自動輪換 | Blast radius = 整個 realm；需手動旋轉 JWKS      | 質性                |
| **S8**  | 鏈路追蹤完整性（從 envelope 反推來源）                       | 完整 L0→L1→L2 issuer chain                                   | 僅最末一段 iss                                  | 質性                |
| **S9**  | 無 mTLS 情境的 MITM                                          | B-mtls / B-full 拒絕                                         | 視 nginx 是否啟用 client cert                   |                     |
| **S10** | 大量驗證請求對中央 endpoint 施壓                             | LSVID 純本地驗證，無中央瓶頸                                 | JWKS 本地快取仍夠用，但 token 撈取仰賴 Keycloak |                     |

### 4.3 量測指標

- **覆蓋率分數**：每組 (拒絕攻擊數 / 攻擊總數)。
- **拒絕延遲**：拒絕一個攻擊請求耗時（對應 DoS 抗性）。
- **質性 rubric（0–3 分）**：
  - 鏈路追蹤完整度
  - 金鑰外洩 blast radius（小 = 高分）
  - 輪換自動化程度
  - 稽核可追溯性

### 4.4 變因控制

- 攻擊腳本對四組使用同一份；只切換 endpoint 與 token 鑄造方式。
- 每攻擊向量送 50 筆，計算拒絕延遲 P50/P95。
- S4（replay）在 K 組對「JWKS only」與「假設加上 server-side jti cache」分別跑兩次，呈現預設配置 vs 加固配置差距。

### 4.5 預期輸出

```
docs/data/exp2-security-{treatment}.json   # 每攻擊向量 pass/fail + 拒絕延遲
docs/data/exp2-rubric.csv                  # 質性 0-3 分矩陣
```

JSON schema：

```json
{
  "treatment": "B-full",
  "vectors": {
    "S4_replay_jti": {
      "result": "rejected",
      "reject_latency_p50_ms": 0.4,
      "samples": 50
    },
    "S6_skip_middle": {
      "result": "rejected",
      "reject_latency_p50_ms": 0.6,
      "samples": 50
    }
  },
  "coverage": "9/10"
}
```

### 4.6 重現步驟

```bash
for T in A B-mtls B-full K; do
  AUTH_TREATMENT=$T scripts/exp/run-security-matrix.sh   # 跑 S1..S10
done
scripts/exp/security-scorecard.py                        # 產生覆蓋率比較與 rubric 表
```

## 5. 實驗 3：儲存空間（LSVID vs X.509-SVID）

### 5.1 命題

量化 LSVID 與 X.509-SVID 在四個維度下的位元組成本，並對 Keycloak JWT 給出對照。預期：

- 單張 X.509-SVID（cert + key + bundle PEM）at-rest 顯著大於單顆 LSVID token；
- LSVID 因含巢狀鏈會在 wire 上隨 hop 線性成長；
- 一筆訂單請求的「身份總位元組消耗」需綜合 at-rest（攤提）+ wire（每跳）+ TLS handshake 才公允比較。

### 5.2 四個量測維度

| 維度                 | 內容                                                         | LSVID 組量測                                            | X.509-SVID 組量測                                     |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------- | ----------------------------------------------------- |
| **Static at-rest**   | 啟動後 SHM 持久化的身份物件                                  | `/tmp/spiffe-shared/x509/0.json`（cert/key/bundle PEM） | 同上（兩者共用 SHM；LSVID 不額外存）                  |
| **Wire per request** | HTTP header / AMQP envelope 中身份載荷 byte size             | `X-LSVID` header；envelope `lsvid` field                | 無（X.509 在 TLS handshake，不在 application header） |
| **Per-hop 鏈成長**   | L0 → L1 → L2 累積大小（含 nested 內嵌）                      | 每 hop 量測 chain depth → byte 曲線                     | N/A（X.509 不延伸鏈）                                 |
| **In-memory cache**  | 程序記憶體中身份物件（解析後 OpenSSL 句柄、validator state） | `LSVIDValidator` + `JtiReplayCache` heap 估算           | `X509Source` + parsed cert chain                      |

### 5.3 量測點（五個）

1. **靜態 at-rest**：直接 stat SHM 檔案（`meta.json`、`x509/0.json`），分欄計算 byte 數。
2. **Wire**：
   - 抓一筆 envelope 序列化後的 JSON，分離 `lsvid` 欄位 vs 其他欄位。
   - 抓一筆下游 HTTP 請求，從 `SpiffeLsvidFilter` 注入點記錄 `X-LSVID` header 完整字串長度。
3. **Per-hop 鏈成長**：`tests/benchmark-lsvid.php:209-218` 已涵蓋 L0..L5；擴充輸出每層位元組長度。
4. **TLS handshake 流量**（B-mtls / B-full 組獨有）：`tcpdump` 量測一次 TLS 1.3 mTLS handshake 中 client / server certificate message 大小。
5. **Keycloak 對照**（K 組獨有）：JWKS endpoint GET 回應大小、單顆 access token JWT 大小、token 撈取一次 RTT 流量。

### 5.4 量測指標欄位

| 指標                               | 單位  | 來源                                            |
| ---------------------------------- | ----- | ----------------------------------------------- |
| `cert_pem_bytes`                   | bytes | SHM `x509/0.json`                               |
| `key_pem_bytes`                    | bytes | SHM `x509/0.json`                               |
| `bundle_pem_bytes`                 | bytes | SHM `x509/0.json`                               |
| `meta_json_bytes`                  | bytes | SHM `meta.json`                                 |
| `lsvid_l0_wire_bytes`              | bytes | benchmark + envelope dump                       |
| `lsvid_l1_wire_bytes`              | bytes | 同上                                            |
| `lsvid_l2_wire_bytes`              | bytes | 同上                                            |
| `keycloak_jwt_bytes`               | bytes | JWT decode 後字串長度                           |
| `jwks_cache_bytes`                 | bytes | Keycloak JWKS GET response                      |
| `mtls_handshake_bytes`             | bytes | tcpdump（B-mtls / B-full）                      |
| `lsvid_validator_heap_bytes`       | bytes | PHP `memory_get_usage` 差分                     |
| `per_request_total_identity_bytes` | bytes | 單筆訂單聚合（at-rest 攤提 + wire + handshake） |

### 5.5 變因控制

- SHM 量測在啟動 + 一次 SVID rotation 後各取一次，避免 race。
- TLS handshake 量測限定單一 connection，禁用 keep-alive。
- 對 LSVID L0/L1/L2 wire 量測使用同一 traceId 避免內容變動。

### 5.6 預期輸出

```

docs/data/exp3-summary.csv     # 每筆訂單請求的「身份總成本（bytes）」
```

JSON schema 範例：

```json
{
  "treatment": "B-full",
  "static_at_rest": {
    "cert_pem_bytes": 2048,
    "key_pem_bytes": 1024,
    "bundle_pem_bytes": 2048,
    "meta_json_bytes": 220
  },
  "wire": {
    "lsvid_l0_wire_bytes": 612,
    "lsvid_l1_wire_bytes": 1340,
    "lsvid_l2_wire_bytes": 2745
  },

}
```

## 7. 限制與假設

1. **Keycloak 驗證模式**：採 `client_credentials` grant + 純 JWKS 本地驗證，**不**啟用 token introspection。理由：反映微服務間最常見配置，且使「替換身份層即可」成立。引入 introspection 將使每跳多一次 RTT，會放大 K 組與 SPIFFE 的延遲差距，但本實驗故意保留 K 組的最有利配置以呈現結構性差距而非配置差距。
2. **拓撲**：所有實驗在單一物理節點 4 容器拓撲，未涵蓋跨地域延遲與大規模水平擴展。
3. **TTL**：SPIFFE TTL 採預設值（X.509-SVID 1h、LSVID 30m），不掃輪換頻率變數。
4. **攻擊面**：安全實驗的攻擊矩陣以「邏輯層」為主，不涵蓋 supply chain、kernel exploit、side channel。
5. **業務不變性**：所有四組必須在 Saga 成功率 ≥ 99% 的前提下才有效；若 K 組 wiring 引入功能性 bug 導致 Saga 失敗率異常，需先修復 wiring 再重跑。

## 8. 三實驗共用流程圖

```
[teardown] → [bring up profile] → [warmup 200 req, drop 50] → [run measurement] → [collect JSON to docs/data/] → [next treatment]
                                                                       │
                                                                       ├─ exp1: stress_test.sh + microbench + saga-e2e
                                                                       ├─ exp2: run-security-matrix.sh (S1..S10)
                                                                       └─ exp3: storage.sh --dim=all
```

最終由 `scripts/exp/aggregate-latency.py` / `security-scorecard.py` / `storage-aggregate.py` 跨四組聚合，輸出 `docs/data/*-summary.csv` 與比較圖。
