# zt-event-gateway 應對策略手冊

> **用途**：症狀導向（symptom-first）的快速排錯查表手冊。
> 一看到症狀 → 跳對應章節 → 看 log keyword、診斷指令、降級開關。
> 架構說明請看 `CLAUDE.md`，本檔只談「**壞了怎麼辦**」。

---

## §0 文件使用說明

**約定**

- 所有 `bash` 指令預設在 repo 根 `/Users/jiezhiyang/zt-event-gateway` 下執行。
- 容器名稱固定：`zt-gateway` / `zt-php-worker` / `zt-spiffe-watcher` / `spire-server` / `spire-agent` / `workload-registrar` / `rabbitmq`；下游各服務分別是 `order-service` / `production-service` / `user-service`，搭配 `order-spire-agent` / `order-helper` 等 sidecar。
- 「主機」= 跑 Gateway+Worker+SPIRE 的那台（`docker-compose.yml`）；「下游主機」= Order/Production/User 三台獨立 Docker（`Services/*/docker-compose.yml`）。
- log 觀察：`docker logs -f --tail=200 <container>`。

**緊急止血三按鈕（依破壞面由小到大）**
| 開關 | 何時用 | 影響 |
|---|---|---|
| `LSVID_REQUIRED=0` | LSVID 解碼或鏈驗證失敗，且懷疑非攻擊 | LSVID 仍鑄造，但驗不過時降級放行（fail-open） |
| `SPIFFE_MTLS_ENABLED=0` | 下游 mTLS handshake 失敗 | 改用一般 TLS / HTTP；身份僅靠 LSVID |
| `SPIFFE_ENABLED=0` | 整個 SPIFFE 層全爆 | 完全停用 SPIRE/SVID/LSVID/mTLS；保留 Saga；需配合 `unset COMPOSE_PROFILES` 或重建 |

**TL;DR — 症狀 → 章節**
| 症狀 | 跳到 |
|---|---|
| `POST /api/orders` 直接 5xx | §2.1 |
| 下單回 200 但 Saga 永遠卡住 | §2.2 |
| 補償流被觸發（庫存被退、訂單被取消） | §2.3 |
| Worker / spiffe-watcher 一直 restart | §2.4 / §3.2 |
| 下游 401/403 或 mTLS handshake fail | §2.5 / §3.6 |
| `order_queue` depth 持續增長 | §2.6 / §3.4 |
| 啟動後 Worker 連不上 SPIRE Agent | §2.7 / §3.1 |
| 想知道某個 log keyword 是什麼意思 | §4 |

## §1 60 秒快速健檢清單（外 → 內）

依「最外層先 → 最內層」順序貼指令；每步附**正常輸出範本**。

### 1. Gateway HTTP 入口

```bash
curl -sf http://127.0.0.1:8080/api/health && echo
```

正常：`{"status":"ok",...}` / 200。失敗 → §3 對應元件，從 spiffe-watcher 與 RabbitMQ 倒推。

### 2. spiffe-watcher SHM 健檢端點

```bash
curl -sf http://127.0.0.1:9901/health | jq .
curl -sf http://127.0.0.1:9901/metrics
```

端口由 `SPIFFE_WATCHER_HEALTH_ADDR=0.0.0.0:9901`（`docker-compose.yml:140`）決定。
正常：`x509.ready=true`、`spiffe_shm_seconds_since_update < 700`。
備援：若 OpenSwoole 未編 HTTP server，端點不存在，這時看 §1.3 SHM 檔。

### 3. SHM 檔案存在 + meta 新鮮度

```bash
docker exec zt-spiffe-watcher sh -c '
  ls -la /tmp/spiffe-shared/ /tmp/spiffe-shared/x509/ &&
  cat /tmp/spiffe-shared/meta.json | head -c 600 && echo &&
  now=$(date +%s); upd=$(grep -oE "\"updated_at\":[[:space:]]*[0-9]+" /tmp/spiffe-shared/meta.json | grep -oE "[0-9]+");
  echo "age = $((now - upd))s"
'
```

正常：`x509_state":"ready"`、`x509_count >= 1`、`age < 700`。

> 這是 docker `healthcheck`（`docker-compose.yml:160`）所用的同一份判斷。

### 4. SPIRE Server / Agent / Registrar

```bash
docker exec spire-server   /opt/spire/bin/spire-server healthcheck
docker exec spire-agent    /opt/spire/bin/spire-agent  healthcheck -socketPath /run/spire/sockets/agent.sock
docker exec spire-server   /opt/spire/bin/spire-server entry show -spiffeID spiffe://zt.local/php-gateway
docker exec workload-registrar test -f /tmp/registrar-ready && echo registrar=ready
```

失敗 → §3.1。

### 5. RabbitMQ 與隊列深度

```bash
curl -sfu zt:ztpass http://127.0.0.1:15672/api/overview | jq '.message_stats'
curl -sfu zt:ztpass http://127.0.0.1:15672/api/queues | jq '.[] | {name, messages, consumers}'
```

正常：每條 queue `consumers >= 1`、`messages` 不持續上升。

### 6. 三個下游服務 health

```bash
for p in 8082 8083 8084; do
  echo "== :$p"; curl -sof /dev/null -w 'http=%{http_code}\n' "http://127.0.0.1:${p}/" || true;
done
```

> 預設使用 `restart-helper.sh` 在 §1.7 之前確保下游 spire-agent 是 fresh 的（多主機部署常踩雷）。

### 7. Saga 端對端探針

```bash
bash scripts/diagnose-order-saga.sh --watch-seconds 30
```

此腳本會：snapshot 所有 saga queue depth → 送一筆訂單 → tail worker log → 報出卡點。
若不熟悉，先讀 `scripts/diagnose-order-saga.sh:1-80` 的 header。

### 8. 一鍵跑全部上述（建議自製 alias）

```bash
docker compose ps && \
  curl -sf http://127.0.0.1:9901/health | jq . && \
  curl -sfu zt:ztpass http://127.0.0.1:15672/api/queues | jq '.[].messages' && \
  bash scripts/diagnose-order-saga.sh --watch-seconds 20
```

## §2 症狀索引（Symptom Triage）

每條：**症狀 → 最可能根因 → 跳章節 → 立即動作（一行）**。

### 2.1 `POST /api/orders` 5xx（請求進不來）

| 根因                                         | 線索                                                                        | 跳節 | 立即動作                                      |
| -------------------------------------------- | --------------------------------------------------------------------------- | ---- | --------------------------------------------- |
| Gateway 容器未起                             | `docker compose ps` 看不到 `zt-gateway` running                             | §3   | `docker compose up -d gateway`                |
| spiffe-watcher 未 ready，gateway 拿不到 SVID | gateway log 出現「Identity token creation failed」/「awaitReady timed out」 | §3.2 | `docker compose restart spiffe-watcher`       |
| RabbitMQ 連不上                              | gateway log 「AMQPConnectionException」                                     | §3.4 | `docker compose ps rabbitmq` + 看 healthcheck |
| LSVID 鑄造失敗                               | gateway log 含 `LSVID` keyword                                              | §3.3 | 緊急 `LSVID_REQUIRED=0` 並重啟 gateway        |

### 2.2 訂單建立後 Saga 永遠卡住

> 跑 `scripts/diagnose-order-saga.sh` 會**直接告訴你卡在哪個 step**。

| 卡點                                                    | 根因                                          | 跳節              |
| ------------------------------------------------------- | --------------------------------------------- | ----------------- |
| `order_queue` 有訊息但 `OrderCreateRequestedEvent` 為 0 | Worker 沒在消費 / RequestConsumer throw       | §3.5 + §4         |
| 卡在 `OrderCreatedEvent`（Step 2 沒跑）                 | OrderService 連線失敗 / mTLS / LSVID aud 不對 | §3.6 + §3.7       |
| 卡在 `InventoryDeductedEvent`（Step 3 沒跑）            | ProductionService 失敗（並發扣庫存）          | §3.5 step2 + §3.7 |
| 卡在 `PaymentProcessedEvent`                            | UserService 錢包扣款失敗                      | §3.7              |
| 沒 `OrderSagaCompletedEvent` 但有 `Rollback*Event`      | 真正失敗已觸發補償                            | §2.3              |

### 2.3 補償流被觸發

- `RollbackInventoryEvent` 出現 → 看 `OrderSaga.php` 線 119-129、150-156、173-179、187-194 任一條件被命中。
- 立即動作：撈 worker log `docker logs zt-php-worker --since 10m | grep -E '\[x\]|Rollback|失敗'`。
- 訂單最終狀態：先打下游 OrderService API 看 `order.status`（compensateOrderAction 應該把它設為 cancelled）。

### 2.4 Worker 持續 restart / 進不到穩態

| 根因                                      | 線索                                                    | 跳節 |
| ----------------------------------------- | ------------------------------------------------------- | ---- |
| SPIRE Agent UDS 不存在                    | `Failed to connect to /run/spire/sockets/agent.sock`    | §3.1 |
| SHM 還沒 ready 就啟動                     | log 含 `Timed out waiting for SPIFFE credentials`       | §3.2 |
| AMQP 連不上                               | `AMQPIOException` / `AMQPConnectionException`           | §3.4 |
| LSVID 強制要求但無法載入 signer/validator | log 「LSVID present on envelope but no LSVIDValidator」 | §3.3 |

### 2.5 下游 401 / 403 / mTLS handshake failure

| 根因                                | 線索                                                                           | 跳節                              |
| ----------------------------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| LSVID audience 不符                 | filter log 「prior LSVID failed re-validation」/「no SPIFFE audience mapping」 | §3.6                              |
| 下游 SPIFFE Agent 失聯 → SVID 過期  | 下游 helper log 沒新證書                                                       | §3.7                              |
| mTLS 開但下游沒收 client cert       | guzzle log SSL handshake fail                                                  | §6.2 立刻 `SPIFFE_MTLS_ENABLED=0` |
| 下游 LSVID_REQUIRED=1 但沒帶 header | 下游回 401 + log 「missing X-LSVID」                                           | §3.6 / §3.7                       |

### 2.6 RabbitMQ 訊息堆積

- `order_queue messages` 持續增長：worker 沒消費 → §3.5 + §2.4。
- 中間 saga queue（如 `OrderCreatedEvent`）堆積：handler throw → log keyword → §4 對應。
- 全部 queue 都堆：worker 整個 down，但若 `consumers > 0` 則表示有連線卻不 ack（看 `unacked` 欄位）。

### 2.7 啟動後 Worker 連不上 SPIRE Agent（最常見開機失敗）

- `docker compose up -d` 之後 worker 立刻 exit。
- 原因：`spiffe-watcher.healthy` 條件未達（`docker-compose.yml:214`）→ worker 拒絕啟動。
- 修：`docker compose logs spiffe-watcher | tail -50` 看為什麼沒 ready，多半是 §3.1 註冊 entry 還沒下發 → 等 60 秒（`REGISTER_INTERVAL=60`）或 `docker compose restart workload-registrar spiffe-watcher`。

## §3 元件分節 troubleshooting

每節格式固定：**徵兆 / 關鍵檔 / 常見 log keyword / 修復步驟（含降級）**。

### §3.1 SPIRE Server / Agent / Registrar

**徵兆**

- 任一服務啟動時卡在 `awaitReady` 超時。
- spiffe-watcher 一直 reconnect，log 反覆 `[spiffe-watcher] gRPC stream …`。
- `entry show` 看不到本服務的 SPIFFE ID。

**關鍵檔**

- `docker-compose.yml:57-89`（spire-server / spire-agent healthcheck）
- `docker-compose.yml:91-125`（workload-registrar，依靠 `/tmp/registrar-ready` 為健康訊號）
- `spiffe/scripts/register-workloads-internal.sh`（registrar 60s 迴圈用的腳本）
- `spiffe/spire-server-e2e/`、`spiffe/spire-agent-e2e/` 設定
- 下游主機：`Services/*/spiffe/` 與該主機自己的 `spire-agent/agent.conf`

**Log keyword**

- `failed to attest agent` — registrar 找不到 agent fingerprint，多半是 cert 路徑錯
- `entry not registered` — registry 還沒收到 SVID 申請
- `x509pop` — agent 用 x509pop attestor 與 server 互信時的 keyword

**修復步驟**

```bash
# 1) 看 server / agent / registrar 三者狀態
docker compose ps spire-server spire-agent workload-registrar
docker compose logs --tail=100 workload-registrar
# 2) 清空 agent 快取，強制重新 attest
docker compose restart spire-agent
# 3) 檢查 entries
docker exec spire-server /opt/spire/bin/spire-server entry show
# 4) 多主機部署：每台下游主機跑 restart-helper.sh
bash Services/Order_service/restart-helper.sh
```

**降級**：無法降級——這是 trust plane，要嘛修，要嘛 §6 全停 SPIFFE。

### §3.2 spiffe-watcher + 共享記憶體 (SHM)

**徵兆**

- `curl http://127.0.0.1:9901/health` 503。
- gateway/worker log 出現 `SHM stale` 或 `Identity token creation failed`。
- 容器 `zt-spiffe-watcher` 反覆 restart。

**關鍵檔**

- `bin/spiffe-watcher.php`（self-heal 邏輯：線 203-236；健檢 endpoint：線 119-186）
- `src/Spiffe/SharedMemory/SpiffeTableStore.php`（writer，seqlock）
- `src/Spiffe/SharedMemory/SpiffeTableReader.php`（reader，`MAX_SPIN=200`、`SPIN_SLEEP_US=500`）
- `docker-compose.yml:154-164`（compose-level healthcheck，吃 700s 門檻）

**Log keyword**

- `[spiffe-watcher] SHM stale (age=Xs, threshold=400s) — exiting for restart` — self-heal 觸發（`bin/spiffe-watcher.php:220-223`）
- `[spiffe-watcher] READY — identity: …` — 正常啟動
- `Health endpoint disabled` — OpenSwoole 沒編 HTTP server，要靠 SHM 檔判斷
- `Timed out waiting for SPIFFE credentials` — reader 端的 awaitReady 超時（`SpiffeTableReader.php:194-199`）

**修復步驟**

```bash
# 1) 看 watcher log + meta.json
docker logs --tail=100 zt-spiffe-watcher
docker exec zt-spiffe-watcher cat /tmp/spiffe-shared/meta.json | jq .
# 2) 重啟（self-heal 已會自動 exit(1) 觸發 restart，必要時手動）
docker compose restart spiffe-watcher
# 3) 若 meta.json 完全沒生 → 多半 SPIRE 沒下發 SVID（§3.1）
# 4) 若 version 是奇數卡住 → writer 中途死掉，重啟 writer 即可重置
```

**降級**：無——watcher 是 SVID 唯一來源。整層停用走 §6 `SPIFFE_ENABLED=0`。

### §3.3 LSVID 簽章鏈 (L0 → L1 → L2)

**徵兆**

- Worker log：`LSVID present on envelope but no LSVIDValidator is configured`。
- Filter log：`prior LSVID failed re-validation`。
- 下游回 401（aud 不符）。

**關鍵檔（鑄造 / 驗證 / 擴展三點）**

- L0 鑄造：`bin/gateway.php`（接 HTTP 後寫 envelope 時的 LSVIDSigner 呼叫）
- L0 → L1 / 入站驗證：`src/Worker/RequestConsumer.php:71-126`
- L1 → L2 / 下游擴展：`anser-gateway/Filters/SpiffeLsvidFilter.php:50-124`
- 下游驗證：`Services/{Order,Production,User}_service/app/...` 中的 LSVID middleware（每個服務自己 verify）

**常見例外 keyword**
| keyword | 出處 | 根因 |
|---|---|---|
| `LSVID present on envelope but no LSVIDValidator is configured` | `RequestConsumer.php:72-75` | wiring：worker 啟動沒讀到 SVID/Validator |
| `LSVID required but envelope carries none` | `RequestConsumer.php:119-122` | `LSVID_REQUIRED=1` 但 gateway 沒鑄造（檢查 gateway env） |
| `Invalid inbound LSVID: …` | `RequestConsumer.php:116` | 簽章 / 過期 / aud 錯 |
| `prior LSVID failed re-validation` | `SpiffeLsvidFilter.php:67-70` | 從事件再進來的 L1 已壞 → 多半是 Trust Bundle 不一致 |
| `LSVID extend failed: …` | `SpiffeLsvidFilter.php:97-101` | signer 拿不到當前 SVID（SHM 失效） |
| `no SPIFFE audience mapping for <url>` | `SpiffeLsvidFilter.php:107-110` | URL → SPIFFE ID 對照表沒設，會 fallback 轉發原 token |

**修復步驟**

```bash
# 1) 確認三個關鍵 env
docker exec zt-gateway env | grep -E 'LSVID_|SPIFFE_ID|SPIFFE_TRUST_DOMAIN'
docker exec zt-php-worker env | grep -E 'LSVID_|ORDER_SPIFFE_ID|PRODUCTION_SPIFFE_ID|USER_SPIFFE_ID'
# 2) 開 payload log 看鏈內容
docker exec zt-php-worker sh -c 'export LSVID_LOG_PAYLOAD=1' # 或改 docker-compose 重起
# 3) 對齊 trust bundle
docker exec spire-server /opt/spire/bin/spire-server bundle show
```

**降級**：`LSVID_REQUIRED=0` → 解碼失敗時 fail-open（`SpiffeLsvidFilter.php:48,71-78`）。臨時用，事後一定要修。

### §3.4 RabbitMQ / 訊息流

**徵兆**

- 隊列堆積 / `consumers=0` / unacked 飆高。
- gateway 或 worker 啟動時 `AMQPConnectionException`。

**關鍵檔**

- `src/QueueTopology.php:15-43`（exchange + 6 條 saga queue + 2 條補償 queue 都是 durable + bind 到 routing key 同名）
- `src/MessageQueue/MessageBus.php`（publish + LSVID extension）
- `src/MessageQueue/RabbitMQConnection.php`（重連、channel 管理）
- 預設用 `events` exchange（direct）+ `order_queue`（`request.new` routing key）→ `.env.example:18-25`

**Log keyword**

- `AMQPConnectionException` / `AMQPIOException` — 連線層
- `UnrecoverableMessageException` — `RequestConsumer.php:33,39,72,116,119,130,155`，會把訊息打到 DLQ（若有設）或 ack 丟棄
- `precondition_code` / `NOT_FOUND - no queue` — topology 沒先建（first run 跑 worker.php 才會建立）

**修復步驟**

```bash
# 1) RabbitMQ 健康
curl -sfu zt:ztpass http://127.0.0.1:15672/api/overview | jq '.queue_totals,.message_stats'
# 2) 重新拉一次 topology（重啟 worker，QueueTopology 會 declare）
docker compose restart php-worker
# 3) 看每條 queue depth + consumer 數
curl -sfu zt:ztpass http://127.0.0.1:15672/api/queues | \
  jq '.[] | {name,messages,consumers,messages_unacknowledged}'
# 4) 卡訊息直接 purge（最後手段，會丟資料）
curl -sfu zt:ztpass -X DELETE http://127.0.0.1:15672/api/queues/%2F/order_queue/contents
```

**降級**：無——RabbitMQ 是必經之路。可改用 single-node `rabbitmq:management` 並重灌。

### §3.5 Saga 編排 (OrderSaga)

**徵兆**：訂單沒結束、queue 卡某一條、補償出現未預期。

**關鍵檔**：`Sagas/OrderSaga.php`（277 行，全是 7 個 EventHandler）

**Step ↔ log marker ↔ 對應 service**
| Step | log marker | 觸發 service | 失敗時 |
|---|---|---|---|
| 1 收到請求 | `Saga Step 1: 收到訂單建立請求`（線 39） | ProductionService（查價）+ OrderService（建單） | `[x] 商品資訊查詢失敗` 或 `[x] 訂單建立失敗`（線 47, 64），**靜默 return**，不發補償 |
| 2 扣庫存 | `Saga Step 2: 訂單建立，開始扣庫存`（線 94） | ProductionService（並發） | `[x] 扣減庫存失敗，觸發補償`（線 120） → `RollbackInventoryEvent` |
| 3 扣款 | `Saga Step 3: 開始支付`（線 143） | UserService | `[x] 支付失敗，開始回滾`（線 149） → `RollbackInventoryEvent`（paymentCompleted=false） |
| 4 確認 | `✅ Saga Step 4: 訂單完成！`（線 198） | OrderService（confirm） | 失敗 → `RollbackInventoryEvent`（paymentCompleted=true，會退款） |
| Comp-2 | `RollbackSaga Step 2: 回滾已扣減庫存`（線 216） | UserService（compensate）+ ProductionService（add back） | 失敗會記 log 但不再補償 |
| Comp-1 | `❌ RollbackSaga Step 1: 取消訂單`（線 240） | OrderService（compensate） | 訂單卡在非 cancelled 狀態 |

**修復步驟**

```bash
# 跑診斷腳本（最有效）
bash scripts/diagnose-order-saga.sh --watch-seconds 60
# 撈一段 saga log
docker logs --tail=500 zt-php-worker | grep -E 'Saga|Rollback|\[x\]|✅|❌'
# 確認下游服務有可達且回 200/JSON
curl -sf http://127.0.0.1:8082/order/{user}/{orderId}
```

**降級**：無 saga 級降級；若卡死可手動 publish 補償事件清理（謹慎）。

### §3.6 下游 HTTP 呼叫 / mTLS / LSVID 注入

**徵兆**：worker log 顯示 SimpleService action `do()` throw、下游回 401/403/SSL error。

**關鍵檔**

- `anser-gateway/Filters/SpiffeLsvidFilter.php:30-141`：beforeCallService 注入 X-LSVID + Guzzle mTLS
- `src/Spiffe/TLS/SpiffeTlsContext.php`（cert/key/ca → Guzzle option）
- `src/Spiffe/SpiffeAudienceRegistry.php`：URL → SPIFFE ID 對照表
- `src/Spiffe/LSVID{Signer,Validator,Mtls}Registry.php`：worker 啟動時填的全域 registry
- `bin/worker.php`：把 SpiffeLsvidFilter 註冊為 Anser global filter

**Log keyword（filter 寫到 STDERR）**

- `[spiffe-lsvid-filter] prior LSVID failed re-validation: …`
- `[spiffe-lsvid-filter] LSVID extend failed: …`
- `[spiffe-lsvid-filter] no SPIFFE audience mapping for <url>`
- `[spiffe-lsvid-filter] mTLS injection failed: …`

**修復步驟**

```bash
# 1) 確認 registry 是不是空的（worker 啟動順序問題）
docker logs zt-php-worker | grep -E 'SpiffeMtlsRegistry|LSVIDSignerRegistry'
# 2) URL → SPIFFE ID 對照表是否含目標 URL
grep -nR 'SpiffeAudienceRegistry' src/ anser-gateway/ | head
# 3) 對比兩端 SPIFFE ID
docker exec zt-php-worker env | grep _SPIFFE_ID
# 下游主機
ssh user@order-host docker exec order-service env | grep SPIFFE_ID
```

**降級**：先 `SPIFFE_MTLS_ENABLED=0`（最常見）；若 LSVID 鏈也壞 `LSVID_REQUIRED=0`。

### §3.7 三個下游 Service（Order / Production / User）

> 三服務 in-tree（Memory：2026-04-27）。每台跑：`spire-agent` + `*-helper`(spiffe-helper sidecar 共享 PID) + 業務 PHP（`webdevops/php:8.2`）+ Postgres。

#### 共通結構

```
Services/{Order,Production,User}_service/
├── app/                     # 業務程式（CodeIgniter + start_service.sh）
├── docker-compose.yml       # spire-agent + helper + service + DB
├── spiffe/
│   ├── certs/<svc>-agent.{crt,key}.pem  # agent 註冊用 cert
│   ├── spire-agent/agent.conf           # agent 設定（指向 zt-spire-server）
│   └── helper/<svc>-service.conf        # spiffe-helper 設定
├── restart-helper.sh         # 一鍵 recreate spire-agent + helper
└── (Postman collection .json)
```

#### Order Service（埠 8082）— `Services/Order_service/`

- SPIFFE ID：`spiffe://zt.local/order-service`（`docker-compose.yml:66`）
- 容器：`order-spire-agent` + `order-helper` + `order-service` + `order_DB`（Postgres :8320）
- DB volume：`./order-db-data`（**不要刪**，含訂單資料）
- mTLS port：18082；HTTP port：8082
- helper 把 SVID 寫到 `/certs`（namedVolume `order-certs`）→ service 端 `SPIFFE_SHM_DIR=/certs` + `LSVID_REQUIRED=0`（線 67-68）

#### Production Service（埠 8083）— `Services/Production_service/`

- SPIFFE ID：`spiffe://zt.local/production-service`
- 同樣的 spire-agent + production-helper + production-service + production_DB
- DB volume：`./production-db-data`
- 商品 / 庫存資料源；Saga Step 1 查價、Step 2 扣庫存都打這裡

#### User Service（埠 8084）— `Services/User_service/`

- SPIFFE ID：`spiffe://zt.local/user-service`
- 多了 `restart-agent-helper.sh`（與 `restart-helper.sh` 略有差異）
- DB volume：`./user-db-data`；錢包資料源

#### 共通修復步驟

```bash
# 1) 進該服務目錄
cd Services/Order_service
# 2) 看狀態
docker compose ps
docker compose logs --tail=80 spire-agent order-helper order-service
# 3) helper 共享 PID 的雷：spire-agent 被 recreate 後 helper 必須一起 recreate
bash restart-helper.sh   # （雙 service 同理：Production_service / User_service）
# 4) SVID 是否落地
docker exec order-service ls -la /certs/
docker exec order-service openssl x509 -in /certs/svid.pem -noout -dates -subject
```

**修復原則**

- 主機端 `spire-server` 重起後，**每台**下游都要 `restart-helper.sh`（雷區）。
- DB 資料保留：千萬不要 `docker compose down -v`，否則 `*-db-data` volume 會被砍。
- 三服務之間沒有 host header / DNS 依賴，主機端 `worker.php` 透過 `ORDER_SERVICE_HOST/PORT` 等 env 直連 IP。

## §6 降級與緊急止血

依「影響面由小到大」排序。任何降級**用完都要驗證、記錄、然後復原**。

### 6.1 LSVID_REQUIRED=0（fail-open）

**何時用**：LSVID 解碼或鏈驗證失敗，但流量不能停（demo / 壓測中）。

```bash
# 主機（gateway + worker）
docker compose up -d gateway php-worker --force-recreate \
  -e LSVID_REQUIRED=0
# 或編輯 docker-compose.yml 線 196, 244 後 `docker compose up -d`
```

**復原驗證**：跑 `composer spiffe:verify` 與 `bash scripts/e2e-full-architecture.sh`，看 LSVID phase 是否全 PASS。

### 6.2 SPIFFE_MTLS_ENABLED=0

**何時用**：下游 mTLS handshake 失敗（最常見：cert 對不上、SAN 缺）。

- 預設值已是 `0`（`docker-compose.yml:248`），若曾改 1 就改回。
- 影響：身份僅靠 X-LSVID（仍簽章），不再 client cert 認證。
  **復原驗證**：`curl --cert/--key` 測下游 :18082 / :18083 / :18084 mTLS 端口。

### 6.3 LSVID_ENABLED=0

**何時用**：LSVID 整層壞、或想做 ablation 比對。

- gateway 不再鑄造 L0；worker `RequestConsumer` 走 `migration-period fallback`（`RequestConsumer.php:124-126`）。
- 配套：worker `LSVID_REQUIRED` 必須也 0，否則矛盾。

### 6.4 SPIFFE_ENABLED=0（核子彈）

**何時用**：SPIRE 整套爛掉，業務還要跑。

```bash
# 1) 編輯 .env：SPIFFE_ENABLED=0
# 2) 不要啟動 zt profile 的容器
unset COMPOSE_PROFILES
docker compose up -d gateway php-worker rabbitmq eventstoredb
# 3) 下游也對應關閉 LSVID 驗證（service 端 LSVID_REQUIRED=0）
```

**注意**：`spiffe-watcher.php:70-73` 有 `SPIFFE_ENABLED=0` 守衛，會直接 `exit(0)`。
**復原驗證**：`bash scripts/verify-spire-integrity.sh` + `composer ci:zt`。

## §7 場景演練 (Playbooks)

### Playbook A — 重啟主 Docker 後，Saga 卡在 Step 2

**症狀**：`OrderCreatedEvent` 收到了，但 `InventoryDeductedEvent` queue 一直是空。
**步驟**

1. `bash scripts/diagnose-order-saga.sh --watch-seconds 60` → 確認卡點。
2. `docker logs zt-php-worker --tail=200 | grep -E 'Step 2|扣庫存|spiffe-lsvid-filter'` → 看 worker 端錯誤。
3. 若是 mTLS / LSVID 失敗：到 Production Service 主機 `bash Services/Production_service/restart-helper.sh`（修 helper 的 PID namespace 失效）。
4. 確認 `docker exec production-service openssl x509 -in /certs/svid.pem -noout -dates` SVID 有效。
5. 重送一筆訂單測通。
   **根因常常是**：主機 `spire-agent` 重啟後，下游 helper 仍綁舊 PID namespace（`Services/Order_service/docker-compose.yml:30-32` 的註解明說此雷）。

### Playbook B — 下游全 401，但 SPIRE 看起來正常

**症狀**：`spiffe-watcher /health` 回 200、`spire-server entry show` 也都在，但 worker 打下游一律 401。
**步驟**

1. `docker exec zt-php-worker env | grep _SPIFFE_ID`（aud） vs 下游真正的 SPIFFE ID。
2. 看 filter STDERR：`docker logs zt-php-worker 2>&1 | grep spiffe-lsvid-filter`。
3. 若 keyword 是 `no SPIFFE audience mapping` → 補 `SpiffeAudienceRegistry`。
4. 若是 `prior LSVID failed re-validation` → trust bundle 兩邊不一致：`docker exec spire-server /opt/spire/bin/spire-server bundle show` 與下游 `agent` 對。
5. 緊急止血：`LSVID_REQUIRED=0` + 修。

### Playbook C — spiffe-watcher 持續 restart，gateway 跟著 5xx

**症狀**：`docker compose ps` 看到 `zt-spiffe-watcher` 反覆 `Restarting`。
**步驟**

1. `docker logs zt-spiffe-watcher --tail=100`。
2. 若是 `SHM stale (age=…) — exiting for restart` → self-heal 在打 gRPC 重連的補丁，多半 SPIRE Agent 有問題：`docker compose logs spire-agent | tail -100`。
3. 若是 socket connection refused → SPIRE Agent down（§3.1）。
4. 若是 `failed to attest agent` → registrar/server 沒接受 agent：`docker compose restart spire-agent workload-registrar`。
5. 確認 healthcheck（`docker-compose.yml:154-164`）會自動帶起 gateway。

### Playbook D — 壓測 30 分鐘後 order_queue depth 暴漲

**症狀**：壓測中（`bash scripts/stress_test.sh`）`order_queue` 從 0 飆到上千，consumer 還在但 processing 變慢。
**步驟**

1. `curl -sfu zt:ztpass http://127.0.0.1:15672/api/queues | jq '.[] | {name,messages,messages_unacknowledged,consumer_utilisation}'`。
2. 看 `consumer_utilisation`：< 1.0 表示 consumer 在處理時太慢。
3. `docker stats --no-stream` 看 CPU/memory bottleneck。
4. 看 worker log 是否大量 `[spiffe-lsvid-filter] LSVID extend failed` → SHM 抖動 → §3.2。
5. 若 unacked 一直累 → worker 連線 idle timeout，重啟 `zt-php-worker`。
6. 找根因前可先 `docker compose up -d --scale php-worker=2`（注意：worker 並不全 stateless，**先確認可重複消費**再 scale）。
